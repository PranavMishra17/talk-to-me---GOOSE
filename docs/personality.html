How we made personality a plug-in

From the Goose voice assistant, November 2026. How one agent can wear any personality and voice, chosen per user or per call, without touching the logic that keeps it safe and fast. Source: talk-to-me---GOOSE at 0048026. A companion to the voice latency handoff.

The short version. A personality is a data file, never code. One YAML file holds everything a personality can change: its voice IDs, its style, its example lines, every line code speaks for it, and its settings dials. The agent's logic reads those through about ten small accessor functions and never branches on which personality is active. So switching personality or voice is one setting, adding a personality is one new file, and privacy, confirmations, tools, hang-up rules and latency work stay exactly the same.

A persona names a default pack, for example goose: {owner: pranav, pack: goose}, but any pack can be put on any persona. That's how Goose, Pranav's assistant, can answer as Jesse for one call and as Jarvis for the next.

2. What a pack contains

Every field is checked when the pack loads, so a broken pack fails at startup instead of mid-call: proxy_core/personality.py#L10. A full example: personalities/jesse.yaml.

3. How a pack is chosen, in order

  1. The persona's default, from config.yaml.
  2. A per-call override in the LiveKit dispatch metadata: {"pack": "jesse"}. The worker accepts it only if it's a real pack, and otherwise keeps the default, because a bad setting must never drop a call. app/worker.py#L143
  3. Whatever sets that metadata: the web API (app/api.py#L62, validated against the pack list), the web picker, or scripts/call.py --pack. A real product would put a settings screen here, writing the same one value.

The voice follows the pack and the provider: app/worker.py#L147. Switching TTS provider in config changes which ID is read, with no pack logic touched.

4. How the agent uses a pack without depending on it

The agent never checks which personality it is. It calls small functions that return text from whichever pack is loaded: proxy_core/personality.py, 85 lines in all.

render_style(pack, stance)          # the prompt block, under about 100 words
greeting(pack, assistant, owner, name)
owner_hello(pack, assistant, owner)
confirm_line(pack, tool, owner)
tool_filler(pack, n)               # rotates, so it doesn't repeat itself
farewell(pack, n)
hangup(pack)
nudge_text(pack, step)
cards()                            # every pack, shaped for a picker

The logic decides when a line is spoken: before a slow tool, before an action, at goodbye. The pack only decides what it sounds like. In app/agent.py#L338, for example, the decision to speak a confirmation is code, and the wording comes from confirm_line(self.pack, ...).

What a pack can never change

  • What a caller is allowed to hear. Every record is filtered by tier in code before the model sees it, and the style block itself says "the privacy filter is unaffected by style". A rude Jesse is exactly as safe as a polite Jarvis.
  • Whether an action needs a yes, how many violations end a call, which tools exist, or the turn-taking and latency settings.

5. Guardrails that keep new packs safe

  • Schema check at load: a missing field fails loudly at startup.
  • Voice-shape tests run on every pack's code-spoken lines: at most two sentences, no lists, at most two options. A new pack with a rambling greeting fails CI. tests/test_personality.py
  • A word budget on the style block, so a chatty pack can't slow the LLM's first token.

6. What we learned the hard way

Lessons
  • Every line the agent speaks must come from the pack. One hardwired goodbye was enough to break character mid-call. The hang-up goodbye now goes further: the model writes it as a parameter of the hang-up tool, and the pack line is only the fallback.
  • Example lines steer more than adjectives. The model copied names and phrasing from them, so keep examples generic or fitted to the domain.
  • Toning a character down needs explicit bans. "Less aviation talk" didn't work until the pack listed the words to avoid and capped references at one per call.
  • Code-spoken greetings put the character in the first word, and cost no LLM time.
  • Pick voices from catalog metadata, then judge by ear. We searched Cartesia's catalog by description (scripts/voices.py) and rendered one in-character line per candidate to choose. Two packs sharing a voice confused listeners, so every pack gets its own.

7. Honest gaps

  • The dials don't drive behaviour yet. They're converted into knobs at load, and the picker shows them. But in this build only the nudge lines are read from knobs, while eagerness, directness, patience and humour are plumbed but unused. If you want dials that change behaviour, wire them into the code that decides when to speak, never into the prompt alone.
  • Voice is tied to personality. If your product lets users choose voice and personality separately, make voice its own setting, with a dispatch metadata override beside pack, and treat the pack's voice as its default.
  • Packs are files. A multi-user product would store them as rows, keeping the same schema check and the same accessor functions.
